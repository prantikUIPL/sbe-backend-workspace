# SBE-1147 Follow-up Plan — Exhibitor Order Details: Bundled-Item Relationships + Signature Image (v1.1 — Approved, FE-aligned)

**Scope:** 1 session. A **purely additive** enrichment of the already-shipped `GET /orders/:orderId` response in `exhibitor-backend-api` (SBE-1147 nested-by-show contract), driven by the Figma UI design. Two independent additions:

1. **Bundled-item relationships on every line** — add three fields to each booth / sponsorship / add-on line (in `shows[]`, `unassigned`, and `additional_purchases[].add_ons`): the line's own `id`, a `is_default_included: boolean`, and a `parent: { id, type } | null` back-reference so the FE can render bundled/complimentary items nested under the line that carries them.
2. **Signature image on the agreement block** — add `signature_url: string | null` to the `agreement` block, a short-lived accessible URL to the captured signature image.

No schema/migration, no new endpoint, no field removals or renames. Nothing existing changes shape.

**Driver:** These are **Confluence-story ↔ Figma-UI reconciliations**, not new scope. The shipped API followed the Confluence story; the Figma design needs (a) bundled items visually grouped under their parent line, and (b) the captured signature rendered on the details page — neither of which the Confluence story (13.3-u called only for the acceptance statement) expressed. Consistent with the SBE-1147 nesting and SBE-1146 invoice reworks, whose driver was the same mismatch.

**Source:** Story 13.3 feasibility — `order_history/13.3-order-details-page/13.3 - Order Details Page.md` (+ `.xlsx`); the nested contract shipped under SBE-1147 (see `13.3 - Order Details Nesting Redesign (SBE-1147) - Implementation Plan.md`). This plan extends that response shape additively.

**Branch:** Rides the existing **`feature/SBE-1147-change-for-ui-design`** branch (already merged to `dev`; rebased onto `origin/dev` so it now carries all of dev + a clean diff for the new work). Commit scope: `type(SBE-1147): …`. Single-track against `dev`.

## Gate Contract

- `GET /orders/:orderId` (owner, product order) still returns HTTP 200 with the SBE-1147 nested shape — every previously-shipped field is byte-for-byte unchanged; this change only **adds** keys.
- **Per-line `id`:** every booth / sponsorship / add-on line (in `shows[].*`, `unassigned.*`, and `additional_purchases[].add_ons`) carries its own `id` — the encrypted `OrderItem` id token.
- **`is_default_included`:** every such line carries a boolean read straight from `OrderItem.is_default_included` (`true` = bundled/complimentary, `false` = purchased).
- **`parent`:** every such line carries `parent: { id, type } | null`. `null` for a top-level line. When non-null, `id` equals the parent line's own `id` token (deterministic cipher) and `type ∈ { "booth", "add_on", "sponsorship" }`. `workshop_pavilion` parents report `"booth"`. The parent line always resides in the **same show** and is itself top-level (bundling is one level deep).
- **`signature_url`:** the `agreement` block gains `signature_url: string | null` — a short-lived accessible URL to the captured signature image (`null` when the agreement has no captured signature, e.g. a manual/offline bypass), resolved via `UploadService.getAccessibleUrl`. The whole `agreement` block is still `null` when the order has no agreement.
- **No removals/renames:** `product_name`, `purchased_name`, `size`, `quantity`, `unit_price`, `setup_fee`, `cleaning_fee`, `subtotal`, `amount`, the four agreement fields, and every top-level field are unchanged.
- Detail-only pure helpers remain unit-tested in isolation; all quality gates green (gitleaks, lint, typecheck, jest ≥80% branch coverage, build).

## Context

**Why:** The Figma redesign renders (1) bundled/complimentary items (default-included add-ons, kit inclusions, booth-attached add-ons) grouped visually **under** the line they belong to, and (2) the exhibitor's captured **signature image** on the details page. The shipped contract exposes neither: lines carry no id, no parent link, and no bundled flag, so the FE cannot associate a child line with its parent; and the agreement block was deliberately scoped to the acceptance summary (signature image withheld per the 13.3-u ↔ 13.3-v split). Both gaps trace to the Confluence story predating the Figma design.

**What:** (1) Extend `ClassifiableOrderItem` + `ORDER_DETAILS_SELECT` / `loadAdditionalPurchases` child select to carry `is_default_included` (id already selected); emit `id`, `is_default_included`, and a `parent` ref from the shared line builder (`classifyOne` / `toOrderLine`); add a new `OrderLineRefDto { id, type }` and add the three fields to `OrderBoothDto` + `OrderLineItemDto`; register the new DTO in the controller's `@ApiExtraModels`. (2) Add `signature_data` to the agreement `select`, inject `UploadService` into `OrderDetailsService`, resolve an accessible URL, and pass it into `buildAgreement` (kept pure) which emits `signature_url` on `OrderAgreementDto`.

## Design Decisions

### D1: `is_default_included` — pass through the persisted boolean

`OrderItem.is_default_included` (Boolean, NOT NULL, already populated: `materializeCartToOrder` copies it from the CartItem; `createDefaultIncludedItems` sets `true`) is added to `ClassifiableOrderItem` and both selects, then emitted verbatim on each line. It is a **reliable flag**, not a `$0`/`unit_price===0` heuristic (a paid item can be default-included; a $0 item can be purchased).

**Implication:** one field added to `ORDER_DETAILS_SELECT.orderItems` (:53–76), to `loadAdditionalPurchases` child `orderItems` (:169–188), and to `ClassifiableOrderItem` (:42–53). Currently unselected/unexposed (grep `is_default_included` in `src/orders` = 0).

### D2: Per-line `id` — expose the already-selected `OrderItem.id`

`ClassifiableOrderItem.id` is already fetched (used server-side for `childrenByParent` / `itemById`) but dropped from the response. Emit it on each line. The global id-cipher interceptor encrypts the universal `id` key automatically → `sbe_…` token on the wire, no manual work.

### D3: `parent: { id, type } | null` via a new `OrderLineRefDto`

For each line, resolve `parent` from `item.parent_order_item_id`: `null` when absent; otherwise `{ id: parentItem.id, type: mapType(parentItem.cart_item_type) }` where `mapType`: `booth`|`workshop_pavilion` → `"booth"`, `addon` → `"add_on"`, `sponsorship` → `"sponsorship"`. The parent row is always in the same `orderItems` array (single-hop, one level deep — `createDefaultIncludedItems` is non-recursive, `validateClientParent` forbids parenting under a default-included line), so it's found via the same `itemById` map used for show attribution.

**Wire encryption:** use a nested `{ id }` on the ref object (the universal always-encrypted key, proven by the shipped `additional_purchases[].show:{id}`), NOT a flat `parent_id`, to avoid the DMMF-column-vs-name nuance in `isEncryptableIdField`. Because the cipher is **SIV-style deterministic** (equal plaintext id ⇒ equal token), the emitted `parent.id` token is byte-identical to the parent line's own `id` token → the FE join `section.find(l => l.id === line.parent.id)` holds on the wire.

**Type-safety of `mapType`:** the parent of a bundled line is only ever a `booth`/`workshop_pavilion`/`addon`/`sponsorship` (never a fee line — fees are folded, never parents; never a default-included line — no grandchildren). `mapType` returns `null` defensively for any unexpected value and `parent` collapses to `null` (a bundled line whose parent can't be typed is surfaced as top-level, never crashes).

### D4: `signature_url` via `getAccessibleUrl` — the house presign-on-read pattern

`OrderAgreement.signature_data` holds an S3/CloudFront URL to the signature PNG (schema comment is stale — runtime writes `signature_data: signatureUrl ?? ''`), or `''` for `is_manual_bypass`/no-file orders, or a `data:` URL for legacy inline signers. Resolve it with `UploadService.getAccessibleUrl(signature_data)` — the exact mechanism used by every other exhibitor endpoint that returns a bucket-stored image (show-discovery `main_image_url`, buy-flow-catalog `images[].url`, shared-cart `proposal_logo_url`, vendor-public). It presigns a short-lived URL for private S3 and passes through in local dev; a `data:` URL isn't key-extractable so it passes through untouched.

**Normalization:** `''` → `null` (bypass orders); a resolved URL → the URL. Emit as `signature_url: string | null`.

**Rationale for A over inline base64 (B):** no endpoint returns base64 on a read path — the base64 route (`resolveSignatureImageDataUrl`) exists only to embed bytes into the DOCX/PDF documents. A presigned URL is small, adds no server-side fetch (presign is local crypto), and matches convention.

### D5: `additional_purchases[].add_ons` inherit the three line fields (shared DTO)

`additional_purchases[].add_ons` use the same `OrderLineItemDto`, so adding `id`/`is_default_included`/`parent` to that DTO means they appear there too. This is intentional and consistent: a child add-on purchase can itself carry inclusions (kit → lanyards), and a `parent` there refers to a line **within that same child purchase**. `loadAdditionalPurchases` already calls `classifyOrderItems(child.orderItems)`, which will thread the same `itemById`/child logic. **Open point pending FE:** if the FE would rather these three fields be omitted on `additional_purchases` lines, that requires a separate line DTO — flagged in §Open Points.

### D6: Keep helpers pure — resolve the signature URL in the service, inject into `buildAgreement`

`buildAgreement` stays a pure sync function; presigning is async I/O. `getOrderDetails` resolves `signatureUrl = order.agreement ? await uploadService.getAccessibleUrl(order.agreement.signature_data) : null` (with `''`→`null`) and passes it as a new parameter to `buildAgreement(agreement, signatureUrl)`, which sets `signature_url`. This keeps the helper unit-testable without mocking S3 and confines the only new I/O to the service.

**Implication:** `OrderDetailsService` gains a `UploadService` constructor dependency (currently `prisma`-only). Update the live-smoke harness, which constructs `new OrderDetailsService(tx as any)` — it must now pass a stub UploadService (or `getAccessibleUrl` passthrough).

### D7: Emit the three line fields from ONE shared builder (no duplication)

Extend `resolveLineNames(item)` (or add a sibling `resolveLineCommon(item, itemById)`) to return `{ id, product_name, purchased_name, is_default_included, parent }`, and spread it into both the booth builder and `toOrderLine` inside `classifyOne`. Single source so booth/add-on/sponsorship lines never diverge and the SonarQube duplication gate stays green. `classifyOne` gains `itemById` as a parameter (both `classifyOrderItems` and `groupClassifiedItemsByShow` already build or can build it).
