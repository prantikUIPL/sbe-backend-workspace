# SBE-1147 Implementation Plan — Exhibitor Order Details Nested-by-Show Response + Product Gate (v1 — Approved)

**Scope:** 1 session. A **breaking** restructure of the existing `GET /orders/:orderId` response in `exhibitor-backend-api` for the FE UI redesign: (1) gate the endpoint to `order_type = product` (non-product → 404); (2) **replace** the flat top-level `booths` / `add_ons` / `sponsorships` / `onsite_contacts` arrays with a **nested-by-show** shape where each `shows[]` entry carries its own `booths` / `sponsorships` / `add_ons` / `onsite_contact`; (3) enrich line items with `product_name` (live) + `purchased_name` (snapshot) and per-booth `setup_fee` / `cleaning_fee`; (4) add a `show: { id }` reference to each `additional_purchases[]` entry. No schema/migration, no new endpoint.

## Gate Contract

- `GET /orders/:orderId` for an authenticated exhibitor who owns a **product** order returns HTTP 200 with `{ success, message, data: {…OrderDetailsResponseDto…}, timestamp }`.
- **Product gate:** a `subscription` or `ppl_addon` order owned by the caller returns **404** `NotFoundException('Order not found')` (mirrors the invoice endpoints; no enumeration leak). Ownership is still enforced server-side (`company_id` from JWT).
- **Nested shows:** the top-level `booths` / `add_ons` / `sponsorships` / `onsite_contacts` arrays are **absent**; `shows[]` entries each carry `{ id, title, city, date, booths[], sponsorships[], add_ons[], onsite_contact }` where `onsite_contact` is a single `{ name, email, phone }` object or `null`.
- **Show attribution:** every booth/sponsorship/add-on line appears under exactly one show; default-included add-ons (null `show_product_id`) resolve to their parent booth's show; a line whose show cannot be resolved is dropped **and** logged (`logger.warn`).
- **Line naming:** every booth / sponsorship / add-on line (including `additional_purchases[].add_ons`) carries `product_name` (live `Product.name`, `null` if the product was deleted) and `purchased_name` (the frozen snapshot, formerly `description`).
- **Per-booth fees:** each booth line carries `setup_fee` and `cleaning_fee` (number, `0` when absent) summed from its `booth_setup_fee` / `booth_cleaning_fee` child lines; `subtotal` still reconciles as `unit_price×qty + setup_fee + cleaning_fee + $0 inclusions`.
- **Additional purchases:** each entry carries `show: { id }` (single-show; the same encrypted token as the matching `shows[].id`); its `add_ons` stay flat.
- **Unchanged top-level:** `id`, `order_number`, `order_date`, `status`, `payment_status`, `financial_summary`, `payments`, `agreement`, `can_download_invoice`, `parent_order`.
- Detail-only pure helpers unit-tested in isolation; all quality gates green (gitleaks, lint, typecheck, jest ≥80% branch coverage, build).

## Context

**Why:** The FE Order Details redesign (SBE-1147) needs the response organized **by show** — each show showing its own booths, sponsorships, add-ons and onsite contact — rather than four disjoint flat arrays the FE must re-group client-side. It also needs product/live names and a per-booth fee breakdown for the new layout. Separately, the endpoint is currently un-type-gated (an asymmetry left by SBE-1621, which gated only the 13.2 listing): a `subscription`/`ppl_addon` order resolves and returns empty sections instead of 404. Without this change the FE cannot render the new design and the details endpoint stays inconsistent with its product-only siblings (invoice list/download).

**What:** Restructure `OrderDetailsService.getOrderDetails` and its pure helpers in `exhibitor-backend-api` so the assembled response nests items under `shows[]`, add a one-line product filter to the ownership `findFirst`, extend `ORDER_DETAILS_SELECT` to fetch `product.name`, add a `groupClassifiedItemsByShow` helper (with child→parent show resolution and per-booth fee breakout), reshape `buildOnsiteContacts` to a `Map<show_id, contact>`, and revise the `dto/index.ts` contract (new `OrderDetailShowDto`; renamed/added line fields; deleted orphaned `OrderOnsiteContactDto`). `classifyOrderItems` stays alive (flat) for `additional_purchases`.

## Design Decisions

### D1: Product gate is a one-line `where` filter, mirroring the invoice endpoint

Add `order_type: OrderType.product` to the ownership `findFirst` `where` at `order-details.service.ts:121` → `{ id: orderId, company_id: companyId, deleted_at: null, order_type: OrderType.product }`. The existing `null → throw new NotFoundException('Order not found')` (:124) then covers non-product orders — same message/pattern as `order-invoice-document.service.ts` `listForOrder` (:177-188). `OrderType` is already imported (:2) and used at :190/:275.

**Implication:** A subscription/ppl_addon order the caller owns now 404s (was: resolved with empty sections). This closes the SBE-1621 asymmetry and reverses that ticket's documented "details is un-type-filtered" behavior — the doc reconciliation (§Docs) is part of this change. No new import.

### D2: `shows[]` becomes the item container — REPLACE, not augment

Introduce a **new** `OrderDetailShowDto` = the four `OrderShowDto` fields (`id`, `title`, `city`, `date`) **plus** `booths: OrderBoothDto[]`, `sponsorships: OrderLineItemDto[]`, `add_ons: OrderLineItemDto[]`, `onsite_contact: OnsiteContactPersonDto | null`. Retype `OrderDetailsResponseDto.shows` to `OrderDetailShowDto[]` and **delete** the top-level `booths`, `add_ons`, `sponsorships`, `onsite_contacts` props and the now-orphaned `OrderOnsiteContactDto`.

**Rationale / implication:** `OrderShowDto` is **shared with the listing** (`OrderListItemDto.shows`, dto/index.ts:102-108) — it must NOT be repurposed; hence a distinct detail DTO. `OrderBoothDto`, `OrderLineItemDto`, `OnsiteContactPersonDto` are reused (not cloned). This is a hard breaking change — see §Backward Compatibility.

### D3: Show attribution via `groupClassifiedItemsByShow` — direct id, else one hop to parent

Add a pure `groupClassifiedItemsByShow(items) -> Map<number, { booths; sponsorships; addOns }>`. For each item resolve its show id as `item.showProduct?.show_id ?? walk(parent_order_item_id → parent.showProduct.show_id)` using a same-set `itemById` map (the parent row is already in `order.orderItems`; no extra select). Classify each line (reusing the extracted `classifyOne` logic) and push into its show's bucket.

**Rationale (proven by the ultracode scan):** booths/sponsorships/fees always carry a non-null `showProduct.show_id`; default-included add-ons (null `show_product_id`) hang off a parent booth via `parent_order_item_id`, and **one hop always suffices** — `createDefaultIncludedItems` is non-recursive and `validateClientParent` forbids parenting under a default-included line, so the parent always carries a real show. For a canonical cart-born product order there are **zero** un-attributable items.

**Implication:** A line whose show id cannot be resolved (only reachable via the checkout-born path — see Deferred) is **dropped and logged** (`logger.warn` naming the order + item), never silently vanished.

### D4: Per-booth fee breakout — `setup_fee` / `cleaning_fee` on each booth line

Fee lines (`cart_item_type` = `booth_setup_fee` | `booth_cleaning_fee`) are children of their booth (`parent_order_item_id`) and are already selected. Instead of only folding their `amount` into `subtotal`, also sum them **by type** per booth into `setup_fee` and `cleaning_fee` (number, `0` when absent). `subtotal` is unchanged: `booth.amount + Σ(all children) = unit_price×qty + setup_fee + cleaning_fee + $0 inclusions`.

**Implication:** Build a `childrenByParent: Map<parentId, children[]>` (carrying `cart_item_type` + `amount`) rather than the current amount-only `childAmountByParent`. `financial_summary.setup_fee`/`cleaning_fee` stay the order-level totals (= Σ per-booth fees across shows) — unchanged.

### D5: Line naming — keep both, rename keys (`product_name` live, `purchased_name` snapshot)

Every booth / sponsorship / add-on line (incl. `additional_purchases[].add_ons`) exposes two name keys:
- `product_name` — live `Product.name` via `item.product?.name ?? null` (null when the product was `SetNull`-deleted).
- `purchased_name` — the frozen purchase-time snapshot, i.e. today's `OrderItem.description` (the `description` key is **renamed**).

**Implication:** Extend the existing `product: { select: { length, width } }` in both `ORDER_DETAILS_SELECT` (:59) and `loadAdditionalPurchases` (:165) with `name: true`. Rename the `description` field → `purchased_name` and add `product_name` on `OrderBoothDto` and `OrderLineItemDto`. `materializeCartToOrder` populates `product_id` on every line, so the live name is reachable for all sections.

### D6: `additional_purchases[].show = { id }` — single-show ref, add_ons stay flat

Each add-on child order is created per-show (`POST purchased-booths/shows/:showId/addon-cart/checkout`), so it is **single-show**. Add `show: { id }` (a minimal `AdditionalPurchaseShowDto`) resolved from the child items' `showProduct.show.id` (already fetched in `loadAdditionalPurchases`). The child's `add_ons` remain a flat `OrderLineItemDto[]` (now carrying the two name keys per D5).

**Implication:** `AdditionalPurchaseDto` gains one `show` property; `classifyOrderItems(child.orderItems).addOns` stays as-is (flat). The token equals the matching `shows[].id`, so the FE maps to fetch the title when it wants.

### D7: `classifyOrderItems` preserved; extract shared `classifyOne`

`classifyOrderItems` keeps its exact signature/return (`{ booths, addOns, sponsorships }`) because `loadAdditionalPurchases` still calls it flat. Extract the per-item classification body into a shared `classifyOne` used by **both** `classifyOrderItems` and `groupClassifiedItemsByShow` — satisfies the no-duplication rule (SonarQube duplication gate).

**Coupling caveat (verified against dev):** the current switch (`order-details.helpers.ts:110-132`, 5 arms — booth :112, workshop_pavilion :113, addon :122, sponsorship :125, default :128) is **not** a pure lift-out — it mutates three outer arrays (`booths`/`addOns`/`sponsorships`.push) and the booth arm reads the cross-item `childAmountByParent` aggregate (:98-104, consumed :119). Fee lines (`booth_setup_fee`/`booth_cleaning_fee`) have **no** dedicated case; they fall to `default` and are folded onto the parent booth via that aggregate. So `classifyOne` must **take the per-parent children aggregate as a parameter** (the new `childrenByParent`) and **return a tagged per-item result** for the caller to bucket, rather than pushing into outer arrays. Feasible, but thread the aggregate in — not a trivial extraction.

### D8: Checkout-born product orders are out of scope — render `shows:[]`, no fallback bucket

`POST /payments/checkout` can create `order_type=product` orders with no `cart_id` / `show_product_id` / `cart_item_type` (Phase-1 flat `custom_amount` pricing; booths unreachable there today). Such an order passes the D1 gate but yields `shows:[]` with all lines un-attributable. **This is not a regression** — today's flat response already drops these items (`classifyOrderItems` switches on the null `cart_item_type`; `buildOrderShows` finds no `showProduct`). Decision: keep them **out of scope** — render `shows:[]` + a defensive `logger.warn` (D3), do **not** add a synthetic no-show bucket (which would make `shows[].id` nullable for everyone) and do **not** 404 them (a viewable order must stay viewable). See Deferred.
